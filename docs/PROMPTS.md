# Scrap Swarm 的五个 Copilot 提示词模板

这些模板服务于“小步实现 → 可观察运行 → 明确证据 → 再迭代”的开发闭环。它们是本项目原创材料，不是其他游戏作者的原始提示词。可直接从 `.github/prompts/` 调用，也可按当前任务复制并补充具体文件、失败证据与验收条件。

## 1. 战斗升级纵向切片

> 阅读 `docs/GDD.md`、`docs/HARNESS.md` 以及相关模拟和场景代码。先用一把武器和一种敌人实现移动 → 自动攻击 → 击杀 → 拾取 → 选择升级 → 恢复战斗，再扩充内容。
>
> 权威规则必须保持固定 tick 和带种子。斜向移动必须归一化；死亡目标只结算一次；升级阶段必须停止 tick 和有效输入，选择应用必须幂等。先添加能失败的确定性回归，再用真实浏览器输入验证路径。只报告实际运行的命令与截图路径。

适用于建立第一个可玩的端到端切片。对应 `.github/prompts/01-vertical-slice.prompt.md`。

## 2. 确定性 Harness

> 扩展现有 Harness，不创建第二套玩法实现。只暴露当前测试需要的类型化、有界预置操作。保留种子、RNG 状态、固定 tick、稳定摘要、事件可见性与生产隔离。
>
> 使用相同种子、初始状态和输入验证三次。确认真实浏览器渲染后重新读取的稳定摘要与纯核心相同，并证明 Canvas 已实际绘制。提供暂停、单 tick 与带版本完整快照，但不要把摘要误称为完整状态。显式断言页面错误、机器人错误和超时不会成为伪成功。运行 `npm run check:prod`。

适用于增加调试入口、复现能力或自动化状态读取。对应 `.github/prompts/02-harness.prompt.md`。

## 3. 战斗反馈与手感

> 编辑前先捕获当前固定场景。只修改前摇/可读性、攻击轨迹、命中反馈或受伤反应；不得改变伤害、冷却、掉落、AI 或经济。玩家、敌人、弹道和危险不能只靠颜色区分。
>
> 修改后以相同种子、构筑、位置和输入复现。检查前后图片并比较事件/状态摘要，证明玩法未改变。若无法实际观察画面，必须标记视觉验收未完成。

适用于只改善表现而不改变平衡的任务。对应 `.github/prompts/03-combat-feedback.prompt.md`。

## 4. 数值或缺陷修复

> 使用失败种子、机器人版本、构筑、输入、事件/状态证据及基线报告。定位一个根规则或一组内聚参数，添加能在当前行为下失败的回归，再做最小修复。
>
> 保持种子集合与机器人策略不变。分别报告胜利、死亡、超时和错误，以及 tick、伤害、承伤、击杀和经济。不得用机器人胜率证明游戏好玩或适合新手。

适用于对局失败、异常状态或数值调整。对应 `.github/prompts/04-balance-fix.prompt.md`。

## 5. 发布前证据清单

> 运行类型检查、lint、单测、生产构建、生产开发控制隔离、Playwright E2E 和代表性机器人报告。不要修复无关系统或扩展范围。
>
> 检查菜单、战斗、商店、首领、胜利与死亡截图，排除空白 Canvas、控件裁切、弹层难读、敌我混淆及反馈缺失。确认机器人报告声明种子集合、样本数、版本、结果枚举与错误。报告精确命令、结果和工件路径；环境阻塞必须明确说明。

适用于最终交付或较大改动后的完整验收。对应 `.github/prompts/05-release-check.prompt.md`。

## 使用原则

- 每次只给 Copilot 一个有边界、可验证的目标。
- 提示词应引用真实路径、失败种子、输入与报告，而不是抽象地要求“优化”。
- 状态测试与截图互不替代：前者证明规则，后者证明画面。
- 自动对局只能发现回归和数值信号，不能替代真人手感判断。
- 只有实际执行并获得退出码的命令才能写入验收结论。
